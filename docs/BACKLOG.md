## B2 · 投递看板

**问题**：`applications` 表 0 行、无接口无页面，用户"投过哪些、下一步干嘛"无处记录。

**做法**：状态机 `saved → tailored → applied → interview → offer / rejected / archived`；
`POST /api/jobs/{doc_id}/application` 推进状态、`GET /api/jobs/applications` 列表；
收件箱详情加状态条、列表加"投递中"筛选；只记 `next_action_at`，不做推送。

**验收**：一个岗位 saved→interview 全程留痕且刷新仍在；同一岗位只有一条记录（已有唯一索引
`idx_applications_doc`）；他人看不到别人的投递记录。

**结果（2026-11-12）**
- 新增 `engine/documents/applications.py` + `application_events` 留痕表：
  `saved → tailored → applied → interview → offer`，任意非终态可 `rejected / archived`，
  归档后能重新 `saved`；非法跳转返回 422 并列出可选状态。
- 接口：`GET /api/jobs/applications`（阶段筛选、每阶段计数、默认排除归档）、
  `GET /api/jobs/applications/{doc_id}`（含留痕）、`POST`（加入或推进，可带备注与
  `YYYY-MM-DD` 的下一次动作）、`DELETE`（移出看板，连带删留痕）。
- 前端岗位收件箱：详情里新增「投递状态」条（当前阶段、备注、下一次动作、可选推进按钮、
  状态留痕折叠列表、移出看板）；列表卡片加阶段徽标；顶部加投递状态筛选与"进行中 N 个岗位"。
- 验收：`tests/test_applications.py` 9 项覆盖 saved→interview 留痕、唯一记录、非法跳转、
  未加入直接推进、账号隔离、归档默认隐藏并可重启、删除连带留痕、删岗位级联；
  真页面走完 加入→定制→投递→面试 并确认刷新后阶段与 4 条留痕仍在。

## B11 · 视觉模型真实效果

## B22 · 自定义 Base URL 被白名单误拦

**问题（用户实测）**：同一个模型配置在 cc-switch / OpenCode 里能用，在本项目里
`POST /api/model-preferences/models?kind=text` 返回 422「该 Base URL 未获准使用，请检查地址或联系管理员添加」。

**根因**：`approved_url()` 要求 `provider=custom` 的地址必须命中 `JOBAGENT_CUSTOM_MODEL_BASE_URLS`
白名单；没配白名单就全部拒绝。而 cc-switch 这类客户端不做这个限制，于是"别处能用、这里 422"。

**修复**
- 策略改为：**公网 HTTPS 端点默认放行**（用户填的是自己的 Key 和自己的服务商），
  只校验 URL 形态（https、无账号密码、无 query/fragment、不直接指向 `/chat/completions`）。
- **内网/本机地址一律拒绝**（SSRF 防护）：`127.0.0.1`、`10/172.16/192.168` 网段、
  `169.254`（云元数据）、`::1`、`localhost`、`.local/.internal/.lan` 等；字面 IP 要求 `is_global`。
- 白名单改为**可选严格模式**：`JOBAGENT_CUSTOM_MODEL_BASE_URLS_STRICT=1` 时才只允许
  `JOBAGENT_CUSTOM_MODEL_BASE_URLS` 里的端点，报错文案直接说明需要加入哪个变量。
- 错误文案也有改进：不再是笼统的"未获准使用"，而是说清是"内网地址"还是"URL 形态不对"。

**验证**
- `tests/test_model_url_policy.py` 9 项：预设与 `/v1` 归一化、第三方公网端点无需白名单、
  http/带密码/带 query/指向 `/chat/completions` 拒绝、内网与本机地址拒绝、公网 IP 放行、
  严格模式仍按白名单拦截、默认模式不拦截。
- 真服务复现同一请求：`https://api.openai-next.com/v1` 与 `https://api.moonshot.cn/v1`
  现在返回 502「服务商拒绝了 API Key」（说明已真正打到上游，用假 Key 才会 401），
  `https://127.0.0.1:8000/v1` 仍返回 422「内网或本机地址」。
- 全量 discover 与前端构建通过；RUNBOOK 环境变量表、`.env.example`、CONTRACTS 第 2 节、
  AGENTS 边界同步更新。

## 设计决策记录

> 早期方案文档（`plan-jobs-knowledge-community.md`）已按实际实现收敛到这里，只保留仍然指导编码的取舍。

**为什么要一层存所有资料**：岗位 JD、用户上传的 JD、面试复盘、技术笔记差别只在 `kind` 与 `source`。
做成两套表会把检索、投稿、审核各写两遍；做成一层的代价只是多两个字段。

**写死的边界（不允许为省事绕过）**

| 不做 | 原因 |
| --- | --- |
| 服务端爬 BOSS / 智联 / 猎聘 | 违用户协议 + 签名/滑块/设备指纹持续对抗，商业化后投诉风险高 |
| 自动投递、自动打招呼 | 平台违规，且对用户是负价值 |
| 真实聊天社区 | 单人无法维护；求职者 3 个月一波流，聊天型社区必然冷掉 |
| 手机号 / 学信网级实名 | 成本远大于收益 |
| 浏览器扩展 | 上架、审核、改版跟进都是长期成本 |

**检索的取舍**：中文分词不用 jieba，改用汉字二元组 + FTS5（零依赖、可复算、断网可用）；
排序退化时只用 BM25 + 时效，不引入 embedding——多一次模型调用就多一个故障点。
公开库**不存别人简历原文**，只收结构化题目与面经，入库前脱敏。

**弱实名后续方案（B8，待产品决定）**

| 档 | 做法 | 成本 | 效果 |
| --- | --- | --- | --- |
| L0 账号可追溯 + 马甲匿名（**已实现**） | 内容绑 `user_id`，对外只显示马甲；映射目前**明文**存库，仅管理员权限保护 | — | 平台能追责，用户敢说话 |
| L1 邮箱验证 + 域名标签（**未做**） | `edu.cn` → 学生；企业域 → 在职；个人域 → 普通。未验证也能看和投稿，只影响排序与审核优先级 | 2–3 天（需 SMTP） | 有"认证感"，天然分出校招/社招两池 |
| L2 手机号 / 学信网 | — | 高 | 不做 |

**风险与对策**

| 风险 | 对策 |
| --- | --- |
| 用户粘贴的链接被平台挡 | 只记录地址、不抓取，让用户改用截图或粘贴正文 |
| 采集源失效（改版 / 403 / 412） | `backend/tools/audit_provinces.py` 人工巡检，失败如实标 `verified: false` 并写原因 |
| 模型不可用导致丢数据 | 导入不依赖模型，`parse_jd` 失败按原文入库并把原因放进 `warnings` |
| 公开内容出现隐私信息 | 入库前程序脱敏；举报进管理员队列；累计举报自动撤下待审 |
| 社群冷启动 | 内容靠真实用户沉淀，不做假数据；机制（审核/互动/时效）先做扎实 |
